# Соответствие требованиям курса и обоснование решений

Документ привязан к формулировкам итогового проекта (мультиагентная система, автоматизация, безопасность, оценка, документация, бенчмаркинг, feedback loop).

---

## 1. Структура и функция (агенты, паттерны, RAG)

| Требование | Реализация | Обоснование |
|------------|------------|-------------|
| ≥ 3 специализированных агента | **Explorer** (EDA), **Engineer** (препроцессинг), **Builder** (модель, submission) | Разделение ролей по этапам Kaggle-пайплайна: от данных к сабмиту. |
| Оркестрация | **Coordinator** (Supervisor) | Явный граф без ручного переключения: один вход `run.py`, одна цепочка. |
| Современные паттерны | Explorer: **ReAct** (рассуждение + инструменты); Engineer: **CoT + Tool Use**; Builder: **Planner–Executor–Critic** (итерации по MSE/гиперпараметрам при LLM-режиме) | Паттерны известны по курсу и литературе по агентам; выбраны под задачи «план → действие → метрика». |
| RAG | **Chroma** + эмбеддинги, корпус `knowledge/`; контекст подмешивается в **Explorer** при непустом индексе | Табличная регрессия + MSE: в базе знаний — практики EDA и регрессии; RAG не дублирует код модели, а поддерживает качество EDA/решений. |

## 2. Автоматизация

| Требование | Реализация | Обоснование |
|------------|------------|-------------|
| Коммуникация и передача данных | Артефакты как **словари** (пути к отчётам, CSV, конфигурация); переходы только через **Coordinator** | Минимум неявного глобального состояния; воспроизводимость и простая отладка. |
| Принятие решений | Подбор гиперпараметров: **сетка / Optuna**; политика **prefer_boosting**; опционально **ensemble** (K-fold blend на test) | Решения по модели фиксируются в конфиге и логах `experiments.jsonl`, а не «вручную в чате». |
| Feedback loop (обратная связь) | **Engineer**: после генерации данных — проверка CSV (`artifact_validation.py`) и при включённых флагах — **`check_python_scripts`** (синтаксис `*.py` в `artifacts/`, `code_validation.py`) и **`check_preprocessor_joblib`** (загрузка `preprocessor.joblib`, наличие `sklearn.pipeline.Pipeline`); при ошибках — **повторный вызов** Engineer с текстом замечаний. **Builder**: при LLM-режиме — Critic по MSE (`builder.py`). | Обратная связь по **данным**, **сохранённому препроцессору** и опционально по **Python-файлам** в артефактах, плюс по **метрике модели**. |

## 3. Безопасность и надёжность

| Требование | Реализация | Обоснование |
|------------|------------|-------------|
| Input validation | `validate_path` — работа только внутри разрешённых каталогов; `validate_model_params` — белый список моделей и границы гиперпараметров | Снижение риска path traversal и некорректных/дорогих вызовов моделей. |
| Guardrails | Белый список имён инструментов; `validate_tool_call` (`guardrails.py`): ограничение длины строк и путей, запрет null-байтов, эвристика по подозрительным фразам в **путях** (`sanitize.py`); лимит числа вызовов инструментов за прогон; сброс счётчика в `run.py` | Сужение поверхности для подстановки «инструкций» в аргументы инструментов; защита от чрезмерного числа вызовов. |
| Мониторинг | Время вызовов инструментов (лог); **LLM usage** в `experiments.jsonl`; при `monitoring.run_summary_json` — **`artifacts/run_summary.json`** (длительность прогона, метрики, `agent_metrics`, ссылки на сабмит) | Воспроизводимое сравнение прогонов без внешнего APM. |
| Устойчивость выдачи (минимум) | `robustness`: опциональный клип предсказаний и/или диапазона числовых признаков (`model_tools.make_submission`) | Не полноценный adversarial-аудит, но снижение влияния экстремальных предсказаний и дрейфа признаков; для отчёта можно описать как ограничение области допустимых ответов. |

## 4. Оценка и бенчмаркинг

| Требование | Реализация | Обоснование |
|------------|------------|-------------|
| Метрики модели | **MSE** на holdout / **K-fold CV**; финальный сабмит при `fit_full_train` или при **K-fold blend** | Согласовано с метрикой соревнования. |
| Эффективность агентов | Агрегирование `llm_usage` в Coordinator; запись в журнал экспериментов | Позволяет сравнивать прогоны (токены, вызовы API). |
| Сравнение ML-конфигов | `scripts/run_benchmark.py` (вспомогательный, не `run.py`) | Несколько моделей подряд на одном препроцессинге. |
| Сравнение «архитектур» системы | `scripts/compare_architectures.py` (например RAG вкл/выкл), метки `--experiment-label` | Отдельно от сравнения моделей — сравнение сценариев мультиагентной системы. |
| Подбор гиперпараметров | Сетка + Cartesian, **Optuna** (`mode: optuna`), опционально **`optuna.models`** (несколько семейств в одном study), **`lgbm_regularization`** (доп. параметры LightGBM), опционально **`preprocessing_search`** — внешний цикл по вариантам encoding / `rare_category_min_count` с Optuna на каждом (детерминированно, без LLM Engineer) | Покрывает benchmarking и сравнение фич/моделей в одном репозитории. |

## 7. Известные ограничения (честно для отчёта)

- Нет произвольной генерации и исполнения кода от LLM — только инструменты (сознательный trade-off безопасности).
- «Атаки» в смысле adversarial ML не моделируются полностью; есть инженерные ограничения (клип, диапазоны), санитизация строковых аргументов инструментов и эвристика по путям — не замена полноценному red-team для LLM API.
- Качество на **private** Kaggle leaderboard не гарантируется локальным CV; рекомендуется фиксировать протокол в `RESULTS.md`.
